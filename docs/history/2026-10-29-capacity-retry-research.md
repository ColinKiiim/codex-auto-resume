# capacity“重试”入口分析与隔离测试 · 2026-10-29

用户本轮明确选择分析测试底部“重试”按钮方案，覆盖此前“仅记录、暂不分析”的安排。本轮只调研、验证原型和更新记录；正式 CAR 仍为 1.1.22，未改恢复逻辑、未发布。

## 结论

机制上可行：当前安装版的 capacity“重试”通过应用自己的空输入继续入口启动任务，不依赖读取输入框文字；自有 Electron 窗口的覆盖与保持最小化协议测试可以投递并确认本地状态变化，前台及鼠标不变。

尚不能把研究原型直接替换进正式版：真实 capacity 按钮的完整 DOM/UIA 绑定样本及服务端恢复闭环本轮未取得；仅匹配按钮名称和错误文案已被反例证明不够。正式方案必须绑定当前聊天的具体失败项，并重核验同一按钮/内容单元，不能全窗口搜索“重试”然后点击。

完全替换现有恢复入口会缩小功能范围：手动暂停或其他没有错误“重试”入口的暂停将无法由该路径处理。初步建议是对已核验的 capacity 失败优先使用“重试”，无此入口时保留现有普通恢复能力；这属于方案建议，尚未成为已实施或已获用户确认的业务改动。

## 当前行为与用户更正

用户明确指出现在只显示“重试”，倒计时是此前方案。研究时从本机安装包找到可选倒计时分支，曾错误表述为当前已启用行为；现以用户实机反馈为准，不能由安装包保留条件代码推断其账号已开启该分支。

代码同时表明，即使显示倒计时，按钮仍允许手动点击，倒计时本身不使按钮禁用；原型兼容样例也在显示 `Retry in 12s` 时立即点击成功。不得由此新增 CAR“必须等倒计时结束”的限制。普通“重试”为本次主要研究对象。

## 真实程序的只读检查

- 本机安装版本：`OpenAI.Codex_26.1021.3705.0_x64__2p2nqsd0c76g0`。先核验本地 6201 监听端口确属此 ChatGPT.exe，再只读查询页面；没有操作真实聊天、切换对话、点击重试或发送内容。
- 发现两个 app 页面；当前可见页有一个编辑器和一个当前聊天侧栏项，另一隐藏页无唯一当前项。两个页面都没有“重试”候选，因此本轮没有实际 capacity 按钮样本，不能据此宣称真机恢复通过。
- 只读查看本机 `app.asar` 内相关模块，原始片段只留本机忽略目录，不进入仓库：`system-error-content-6635ad9baa36.js`、`start-turn-9b023c2c2159.js`、`app-initial-438d1df57f70.js`、`local-conversation-turn-c0f4769f8388.js`、`app-shared-955d52676f9c.js`。

相关代码关系：

1. capacity 类型 `serverOverloaded` 使用独立错误卡片与重试入口。该入口显示前检查会话就绪、对应轮次是最新一轮且状态为失败；历史 capacity 文案可以继续保留，但不等于仍存在可用的对应按钮。
2. 普通错误/环境准备失败也有重试类入口；“Retry / Try again / 重试”不是 capacity 的专属名称。额度耗尽还走不同的提示分支，不能统统当作 capacity。
3. capacity 手动重试回调使用 `capacity_retry_manual`，调用 `start-turn` 模块导出的空输入继续入口；该入口再调用 manager 的 `startEmptyTurn`。按钮回调没有从编辑器取文本，也没有要求输入框为空。
4. 实际空输入入口在未显式提供 continuationInput 时传递空输入列表，应用已有任务运行中检查；这不表示 capacity 会消失或服务器必定接受请求，也不等于已经完成真实服务端测试。
5. 错误卡片底层以 `aside` 呈现；对话内容包装代码存在 `data-content-search-unit-key`。后者只是内容单元身份，不是“此节点一定是 system-error”的证明，不能孤立当作动作授权。真实错误卡片是否总有该包装、其与聊天/最新失败轮的映射，仍需故障机样本确认。

## 隔离测试

使用本机已有 Electron 45.1.0 独立配置、独立页面、随机调试端口和自有窗口，不启动正式 CAR 监测，不操作真实 ChatGPT。窗口放置在屏幕外，覆盖样例核对自有覆盖窗口可见且几何范围包住目标；这是协议/自有窗口验证，不冒充故障设备上的全屏应用遮挡验收。

### 原型和反例

18 次聚焦断言通过，包括一个刻意构造的错误识别反例及其排除样例，并非 18 个真实设备/服务端场景：

| 检查 | 结果与边界 |
| --- | --- |
| 简单匹配“capacity 文案＋重试” | 在其他区域伪造同类卡片，简单原型确实误点；据此否定全窗口文字匹配即可安全使用的做法 |
| 绑定内容单元的研究原型 | 排除上述不属于对话内容的卡片；真实 system-error 类型/最新轮身份仍待实机确认，不能声称排除了所有仿同内容 |
| 普通中文“重试”、英文 Retry | 分别只触发一次本地继续，状态转为运行 |
| 有输入文字 | 检测/点击没有读取或改写编辑器，已有文字保留；探针对编辑器文本 getter 设置抛错并记录读取次数，结果为零，不引入草稿门槛 |
| 可选倒计时兼容样例 | 不等待倒计时结束即可点击；不把该样例当作用户当前界面 |
| 对话改变、错误按钮节点替换 | 旧观察不再授权动作 |
| 多候选、任务已运行、按钮已禁用 | 不点击 |
| 用户输入让行 | 原型注入 1499ms 空闲样例被阻止；这是模拟边界，不代替正式进程的 Windows 输入复核；正式接入必须继续复用已有 1.5 秒让行 |
| 投递后结果不明 | 同一候选不重复投递；不能把点击返回当作恢复成功 |
| 历史错误只有文案、无对应重试；其他位置只有 Retry | 均不授权点击 |
| 自有窗口被覆盖 | 通过 CDP 点击一次并观察本地状态转为运行；目标未最小化 |
| 自有窗口最小化 | 点击后仍最小化，投递一次并观察本地运行状态 |
| 桌面影响 | 前台句柄、鼠标位置保持；测试结束自有 Electron 退出，无遗留该运行时进程 |

原型主要验证控件投递能力与动作前绑定，不包含正式 CAR 的完整账号/额度/时间/问答策略，也没有人为引发真实服务器 capacity。模拟 handler 的计数与状态不属于服务端成功证据。

### 安装版原生入口的离线检查

另从安装包提取实际空输入入口函数，在隔离 JS 上下文中执行，manager 和请求投递均用本地替身，无网络/真实应用动作。4 次必要断言通过：

- 最新失败且空闲时，向原线程提交空输入列表，不从输入框取文字
- 首次投递使本地替身进入运行后，再调用不产生第二个请求
- 已运行状态不投递
- 会话尚未就绪时拒绝，不投递

这补充验证了所读原生函数的语义，不是把安装包代码运行在真实聊天中，也不是服务端恢复验收。

### Windows UIA 的边界

同一自有窗口的只读 UIA 探针首次在覆盖阶段未返回重试按钮，之后最小化阶段能返回按钮及 InvokePattern，且 `IsOffscreen=false` 与 Win32 实际已最小化同时存在。这里只能说明 UIA 结果有初始化/提供者状态差异，`IsOffscreen` 不能证明目标未最小化或数据新鲜；不能据此得出所有 UIA 提供者均失效或该按钮必定可正确后台调用的结论。

最小化仍应沿用已核验的 CDP 路径；无该接口时不得因能找到一个 UIA 名称便假称已获得最新错误状态，也不把截图坐标作为最小化点击依据。

## 建议的正式接入步骤

1. 取得真实 capacity 时的只读控件元数据，记录页面/进程/当前聊天、错误项或内容单元身份、按钮名称/可用状态及观察时间；不读取输入框，不捕获不相关聊天全文。
2. 定位当前聊天最新失败项里的唯一 capacity 重试按钮；确认其不会来自历史、侧栏、工具结果、文档或其他 app 页面。真实结构不支持核验时，不启用这一新动作路径，不扩大成任意重试文字搜索。
3. 在已确认候选上投递原生按钮动作，动作前重核验同一页面、聊天、失败项和按钮实例；已有输入让行、问答、额度/计划和目标绑定策略复用。普通恢复没有输入文本检查，也不新增“有草稿不点”条件。
4. “已投递”与“已恢复”分开记录；复核新轮次/真实运行或可核验的完成状态，错误卡片消失或 click 返回单独不足以确认成功。结果不明不重复投递；持续 capacity 应作为新的已核验失败状态处理，不能使用旧候选无限点击。
5. 对同一失败只能选择一个恢复入口，避免重试和蓝色恢复按钮同时触发。实施前明确完全替换还是 capacity 优先；本轮没有改变普通暂停的行为范围。
6. 用故障电脑补齐前台、完全遮挡、最小化、持续 capacity、真实点击后新轮次确认和持续用户操作时让行。自有 Electron 与离线函数结果不代替这些实测。

该路径能减少对图标形状/截图新鲜度的依赖，但“换一个按钮”本身不会让旧截图变新；仍需使用实时控件接口。1.1.22 已通过用户的遮挡/目标最小化验收，本研究不将该既有修复重复归功于尚未接入的重试方案。

全部脚本、安装包片段及原始结果保留在本机忽略目录 `.local/retry-research-20261029/`，未增加长期重复测试或修改正式源码。

## 补充：用户停留在聊天中部 · 2026-10-29

用户指出重试在最底部，而实际视口可能停留在聊天中部。上一轮只验证覆盖/最小化，没有单独覆盖这种内部滚动状态；两者不能混为同一项验证。本轮补测后区分如下：

| 底部按钮的实际状态 | 结果 |
| --- | --- |
| 仍在 DOM，只是处于整页视口下方 | CDP 原型可以直接点击，不需先滚到底部；样例中页面滚动停在 2000，按钮顶部约 3071、视口高 518，点击前后滚动位置不变 |
| 仍在 DOM，但在嵌套滚动容器的可见范围外 | 可直接点击；同时核对外层页面和内层容器的滚动位置保持 |
| 祖先设置 `content-visibility:auto`，离屏内容暂缓绘制 | 本次 Electron 夹具仍能查询和点击，未滚动。安装版 `local-conversation-turn` 的部分内容包装确实使用此 CSS；这不是节点已经被卸载的证明 |
| 虚拟化把按钮真正移出 DOM，或以 display:none 隐藏 | 原型找不到可用候选，不点击；不能使用旧坐标或之前缓存的节点补点 |
| 观察后节点被卸载，再生成新节点 | 旧观察失效；必须重新观察、核验新节点后才允许一次投递 |
| 目标既最小化，又停在聊天中部，按钮仍在 DOM | 样例仍可投递并保持最小化和内部滚动位置 |

补充探针有 10 次聚焦断言通过，使用独立样例状态；观察后卸载/重挂载在同一状态内验证，没有删除或绕过此前的重复投递保护。检测/动作仍没有读写编辑器，前台和鼠标不变。结果保留于本机 `.local/retry-research-20261029/scroll-1793275411572/results.json`；夹具及脚本同目录系下，不进入源码包。

关键区别是“是否仍存在于可核验的 DOM/控件结构”，不是“人眼当前是否能看到”。原型现有可用性检查采用渲染几何、隐藏属性等，未把按钮与视口相交作为必要条件；未来正式接入也不能错用“屏幕内可见”条件排除正常离屏按钮。截图识别/坐标点击不能解决此场景。

若真实长对话的最新错误项被虚拟化卸载，重试路径自身无法直接操作。初步方案优先保留现有普通恢复入口作为这种情况的后备，避免为找按钮强制改变用户阅读位置；如果最终选择完全替换现有入口，则必须先解决真实页面中卸载项的可靠定位，不能直接假定自动滚底即可。此处仍是方案分析，没有在正式 CAR 增加自动滚动或新分支。

测试 handler 只更改本地运行状态，没有模拟真实 Codex 新轮次开始后的全部界面行为。真实应用可能在继续任务时自行滚动，因此“CAR 的 DOM 点击不需要先滚动”不等于“真实应用恢复后一定维持阅读位置”。故障电脑还需在长对话中部分别核对：最新错误是否挂载、是否可正确绑定、实际恢复是否成功，以及恢复前后是否发生应用自己的自动滚动。

## 补充：真实长聊天节点保留测试 · 2026-10-29

用户进一步要求直接验证是否会发生底部节点卸载。本轮针对本机实际运行的上述安装版应用测试，不再只用自有 HTML 模拟。

- 重新核验 6201 端口属于该安装版 ChatGPT.exe；唯一已绑定聊天页面有一个 `.thread-scroll-container`，总高 13,082、可用高 1,004。页面当时处于后台，`document.visibilityState=hidden`；另一无唯一当前聊天的 app 页面不操作。
- 测试前记录 13 个内容单元的节点引用和身份，重点保留底部 3 个节点的引用；不读取输入框或聊天正文。先把内部滚动位置从 11,840.7998 临时调到 6,039.2002，再调到 0，各等待 1.1 秒让页面处理滚动。
- 在中部和顶部时，全部 13 个原始内容节点仍连接在原容器中；底部 3 个节点的身份与对象均未变化，仍有渲染几何。中部时它们位于视口下方约 6,286～6,519，顶部时约 12,326～12,558，而非被移出 DOM。
- 测试后内部滚动恢复为 11,840.7998，误差 0；聊天绑定不变、没有用户操作与测试交错，前台句柄、鼠标位置和 Windows 最近输入 tick 均保持。没有切换聊天、点击按钮、发送消息或激活/还原窗口。

结论：本机该版本、该实际长聊天在后台滚到中部/顶部，没有复现底部内容被虚拟化卸载的问题。此前“按钮可能被移出 DOM”应继续视为一般技术边界，不能当成已发现的当前应用缺陷，更不能因此默认强制滚到底部。

限制：该聊天实际 capacity 卡片和重试按钮数量均为 0；观察到的是正常内容单元的保留行为，不能把它写成真实 capacity 按钮保留/点击/恢复闭环已通过，也不扩展为所有更长聊天、前台状态或其他版本的保证。结合此前安装版重试组件按最新失败/就绪状态显示的代码检查，尚无证据表明仅滚动到中部会移除该按钮；故障机出现 capacity 时仍需对真实错误项补最后一次确认。
