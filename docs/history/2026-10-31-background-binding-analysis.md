# 1.1.24 后台绑定持续不可核验：分析与待实施方案

用户要求：分析截图与下载目录诊断 ZIP，解释为何不自动刷新、为何暂停再开始可恢复；本轮不实施修复、不构建或发布。以下仅为调查记录与建议。

## 证据与结论

- 分析对象为 1.1.24 源码，当前提交 `9feaa76`；诊断包生成于 2026-10-31 01:15，时间为设备本地 UTC+8。未执行诊断包内程序或将包内文字当作操作指令。
- 01:12:33 最后一次成功读取来自 CDP，状态 Running；01:12:35 报 `app-page-window-unmatched`，01:12:41 起持续报 `conversation-identity-ambiguous:2`。截至 01:15:25 共 32 次不可用记录，约 170 秒没有重新取得有效状态。窗口仍有效、未最小化，后台捕获工作线程未忙，恢复尝试/确认维持 4/4。
- 更早的 00:52:35 至 00:55:15 已出现同类 CDP 身份歧义。00:55:16 暂停、00:55:17 开始，00:55:18 即取得 UIA Running；该成功记录的 binding-note 仍明确携带同一个 CDP 身份歧义。这直接支持“重新开始启用后备通道”，而非“暂停操作修好了 Codex 页面”。00:46 和 00:51 也有暂停再开始恢复状态读取的记录，但原错误分别是页面匹配失败和超时，不能都算作同一个触发原因。

## 代码路径

1. `src/BackgroundControls.cs` 的 `TickBackgroundControls`：已绑定 CDP 时，每次观察都传入旧 `backgroundContext`。失败只清理显示与连续观察、等待 5 秒，保留 context 与 `backgroundControlsActive=true`。
2. `src/ComposerWorker.cs` 的 `Run`：只有 `request.Context == null` 才按“发现端口 → 尝试 CDP → 打开失败后尝试 UIA”执行。已有 CDP context 则直接打开 CDP，失败跳到外层返回 Blocked，不执行 UIA 后备。因此重试虽然每次都会创建新的辅助进程/连接，但一直重复携带相同绑定的路径；不是辅助进程始终卡住。
3. 绑定后读取失败仍返回 true，`src/App.cs` 的 `TickMonitor` 提前返回，不进入 `TickBackground`。图像分支中的捕获 watchdog/独立捕获不负责修复语义绑定，当前路径也不会到达它。不能把旧图像改成可点击状态来解决。
4. `Stop` 增加 `generation`；重新开始后下一次控件轮询发现 revision 改变，会清空 `backgroundContext`、`backgroundControlsActive` 和冷却时间，重新进入允许 UIA 后备的首次绑定路径。
5. `src/composer-runtime.js` 在已找到唯一主编辑器后，仍在整个 document 查询 `[data-above-composer-conversation-id]`。过滤仅排除 aria-hidden/inert，未把元数据约束在该编辑器的当前聊天容器内；只要有元数据便不采用侧栏 ID，两个不同的规范化 ID 就直接抛错。`:2` 指两个不同候选 ID，不是两个相同 ID 的重复节点，也不是识别到两个恢复按钮。

确定的缺陷是失败后的绑定恢复/后备路径不完整；全页元数据选择过宽是已由源码确认的脆弱点。两个 ID 实际分别属于哪个容器、是否源于切页残留/并存页面，及首次页面匹配失败是否由标题或页面替换触发，现有包不能进一步确认。窗口移动、截图中的桥接网络错误与该故障没有足够因果证据；CAR 日志显示的是本地页面/聊天绑定失败。

## 已做的定向验证

使用 Node vm 直接加载未修改的 `src/composer-runtime.js`，提供最小合成 DOM，保持唯一主编辑器和相同容器：单一元数据 ID 能绑定；重复相同 ID 能绑定；两个不同 ID 精确复现 `conversation-identity-ambiguous:2`。该探针验证选择器的失败条件，不代替真实 Codex DOM 重现、后台动作或设备验收。未运行真实点击、停止/继续、发送、刷新页面或其他写入目标应用的操作。

## 建议的修复顺序（尚未实施）

1. **补齐只读重新核验**：绑定连续失败达到有限阈值后，在当前 HWND/PID/进程启动时间约束内重新发现页面/端口与控件；例如 2–3 次失败后进入，成功即恢复正常频率，持续失败采用有上限退避。把“用于恢复监测的候选绑定”与“用于授权动作的已验证上下文”分开，允许只读 CDP 重新发现及 UIA 后备；避免把 observe 的错误恢复扩展到 resume/pause/submit 的动作执行。
2. **修正身份来源范围**：元数据优先从主编辑器对应的当前聊天区域取证，结合页面路由/原生主文档与侧栏独立佐证。不能仅加 visible 过滤，因为合法元数据锚点可以是零尺寸；也不能取第一个 ID、只选旧 ID、全局清空 DOM 或忽略冲突。无法证明候选归属时继续只读等待。
3. **保持动作与业务状态**：重新绑定不得调用 Stop/Toggle。它们会取消定时恢复、重置额度暂停，且已有定时恢复时可能关闭自动恢复。保留用户设置、定时/额度所有权、账号约束及已经投递的动作/失败去重记忆；取消或隔离旧上下文在途请求，防止迟到结果被采用。CDP 与 UIA 的 Conversation 不是同一种 ID，现有 SameConversation 会将跨后端视作变化；必须明确处理跨后端身份和原有投递确认，不能直接清空旧 context 来跳过检查。无法证明同一目标的定时、额度或范围绑定继续阻断动作；不能把 UIA 标题相同当作同一聊天的充分证明。
4. **重新取得新证据后再动作**：候选后端独立核验当前窗口/聊天/输入区、账号与范围及问答状态；重建连续观察，并保留 1.5 秒输入让行。旧证据不得授权点击；最小化时保留必须有可核验 CDP 的限制，不用缓存 UIA 或截图后备。
5. **改进诊断与提示**：记录失败类别、旧/新后端与页面指纹、候选数量/所属容器类别、重新发现阶段/耗时/结果与阻断原因；仅存指纹与结构，不存聊天正文。明确区分正在自动重新绑定、身份仍有冲突和需要用户确认，避免长期仅显示“等待重新确认”。

## 最小验收范围

- 已绑定 CDP 后出现元数据双 ID/页面替换/旧端口失效，UIA 可核验时无需手动暂停即可重新取得新状态；两后端都不能核验时保持只读，不循环创建无界进程或误报恢复。
- 元数据属于旧页面/其他区域、两个当前有效候选、同名聊天、主编辑器替换、125% DPI 页面移动分别正确处理；有真正歧义时不能自动选择任一目标。
- 原动作已投递且确认不明时自动重绑不重复投递同一失败，不把另一聊天 Running 记为原动作成功；后台切换不能绕过账号、额度/定时/范围及问答保护。
- 目标遮挡/最小化与用户持续输入时保留现有行为；重新绑定不激活目标、不移动鼠标、不取消用户配置或额度暂停所有权。
- 先做少量对应缺陷的定向回归，再在实际 1.1.24 故障设备复现同类页面状态，核对恢复日志；本轮未将方案标记为修复或实机通过。
