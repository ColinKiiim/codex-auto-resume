# 2026-10-26 真实 Codex 输入框读写探测

## 范围与方法

- 用户授权当场验证输入框写入可行性；仅操作本机已打开的真实 Codex 桌面输入框，不创建新对话、不点击停止或发送、不提交消息
- 目标为已安装的 OpenAI.Codex 26.1016.8622.0 Windows x64 应用，不是 CAR 演示窗口
- 通过 computer-use 的 Windows 无障碍快照和 `sky.set_value` 接口检查；另外只读采集 Win32 前台窗口与鼠标位置，用于区分可写能力和后台无焦点能力
- 开始前截图确认输入框为空；无障碍树显示 `编辑 (settable, string)`，空框的 Value 和 document_text 均返回占位文字“和 Codex 一起工作”，不能把这个值直接当成真实草稿

## 实际观察

1. 激活已有文件资源管理器，使其保持前台；后台读取 Codex 无障碍信息后，前台仍是资源管理器
2. 对快照中的编辑控件调用 `sky.set_value`，设置临时中文文本“CAR 后台输入验证 2026-10-26 — 临时草稿，不发送”
3. 调用返回成功，无障碍编辑控件的 Value 和 document_text 均完整读回同一段文字
4. 写入前后鼠标位置相同，但前台窗口由资源管理器变成 Codex；这条测试路径不满足不抢前台的要求。工具 API 文档已说明输入方法会自动激活目标窗口，因此该现象不能归因于 Codex 原生 UIA setter 必然需要前台
5. 再次确认草稿仍严格等于测试文字后，以空字符串还原；读回恢复为空框占位文字，无发送动作

## 结论与尚未验证部分

- 已确认：本机真实输入框可以被现有无障碍工具定位；该工具的设置文字操作能写入中文并读回，随后可清除
- 未确认：CAR 直接调用原生 UI Automation `ValuePattern.SetValue` 时，能否在目标完全遮挡、保持其他窗口前台和焦点不变的条件下写入并正确触发输入框内部状态更新。本次没有运行原生 setter 探针，不能把工具调用成功写成原生后台路径已通过
- 工具路径的限制来自 computer-use 的 API：输入操作自动激活目标窗口；该技能要求 Windows 应用自动化仅使用其 JS API，本轮未混用另一套 UIA 操作路径
- 后续仍需验证：原生 UIA 模式支持及无焦点读写、原对话核验、附件/草稿/问答保护、输入变化取消、发送按钮启用状态与单次发送后的确认；本次不覆盖发送成功、额度恢复闭环或第二台实体设备
- 该结果只缩小实现不确定性，不代表“额度恢复后补发继续指令”功能已完成或发布；后续实现应使用 CAR 可直接调用的系统接口，不依赖安装 computer-use 插件
