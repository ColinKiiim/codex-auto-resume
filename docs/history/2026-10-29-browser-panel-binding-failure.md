# 内置浏览器/紧凑聊天布局导致后台核验失效 · 2026-10-29

用户截图显示聊天缩在左侧、右侧内置浏览器打开登录页；左侧 capacity 错误旁有“重试”，CAR 却持续显示“后台控件暂不可核验，等待”。截图的最后有效控件时间为 20:26:49，而近期检查进度已到 20:33；旧方块预览不应被理解为当前仍在运行。

本轮完成源码定位、自有窗口对照，以及故障机直接只读核验。确认是现有绑定逻辑的布局兼容缺陷，正式程序尚未修改或发布；前几轮重试研究仅修改文档/本地探针，没有把重试方案装进故障机。

## 故障机直接证据

通过已连接 MiniPC 工具确认是截图对应的故障设备，运行 CAR `1.1.22.0`、应用安装包 `OpenAI.Codex_26.1023.6621.0_x64__2p2nqsd0c76g0`。此版本不同于先前本机节点保留测试使用的 26.1021，不能把本机样例当作该机全部布局兼容性证明。

对正在运行的真实目标调用原版 EXE 的 `--composer-worker`，操作限定为 `observe`，结果为：

```text
Result=Blocked
Stage=open:ComposerUnavailable:conversation-count-0
BindingNote=CDP-unavailable:ComposerUnavailable
ContextPresent=false
ActionAttempted=false
```

随后只读 UIA 元数据确认：

| 绑定所需信息 | 故障机实际结果 |
| --- | --- |
| 非空命名的 RootWebArea 文档 | 2 个，位于同一应用窗口 |
| 主聊天 ProseMirror 编辑器 | 唯一，且可定位其所属网页文档 |
| 聊天标题工具栏与该所属文档标题 | 1 个匹配 |
| 原实现要求的同名侧栏 ListItem 按钮 | 0 个 |
| 其他编辑控件 | 另有 2 个非主聊天编辑控件；未读取其值 |

已有调试端口也重新核验了所属进程。当前 app 主页面只读检查同样得到当前侧栏选中行 0；另有快速聊天 app 页面，不能任意挑选 app 页面。主页面存在聊天相关数据属性，但正式可用的稳定聊天身份及其作用域仍需验证；不能看到某个属性就直接删掉原身份保护。

只读检查当时未找到普通“重试”候选；这不改写截图当时已有 capacity 的事实，也不作为重试闭环测试。没有点击、发送、读取输入框内容、切换聊天、改变前台或安装/重启远端程序。

## 精确失败路径

1. `ComposerWorker.cs::CodexDocument` 从整个窗口收集所有命名 RootWebArea，仅数量等于 1 才返回文档。故障机为 2，因而返回 null，没有按主聊天编辑器所属文档区分聊天与浏览器。
2. `BuildContext` 随即退回通用选中项路径；该布局没有符合条件的选中项，抛出 `conversation-count-0`，与实机返回完全一致。
3. 即使只修正文档作用域，原有主路径仍要求同名侧栏 ListItem 按钮；故障机该数量为 0，还会遇到第二个 `codex-conversation-structure` 障碍。因此不能仅把“文档数量”条件改松便宣称修好。
4. `DebugComposer` 在连接 CDP 页面前也先构造 `AccessibleComposer` 取得原生证明；这一步同样失败，产生 `CDP-unavailable:ComposerUnavailable`。所以已有 CDP 端口并不能绕过本缺陷。
5. `BackgroundControls` 在之前已建立过绑定后，失败会每隔一段时间重新读，并保持等待，不退回旧图点击。布局不变时同样的绑定条件一直失败；“等待”不代表已经正确检测到当前暂停或运行。

这是读取聊天身份前失败，不是因草稿而拒绝恢复，也没有证据显示本次发生了误点击。程序不应因正常展开内置浏览器而长期失去恢复能力；保留失败时不乱点的行为，不等于此兼容缺陷无需修复。

## 正式版对照复现

使用独立 Electron 窗口、独立配置与命名为 `OpenAI.Codex_fixture` 的自有运行路径，触发现有 Store 布局识别分支。窗口包含聊天文档、工具栏、侧栏当前项、主输入区和恢复按钮；仅调用正式 1.1.22 的 observe 辅助进程。自有目录链接不修改或伪装真实安装包，不使用该夹具对真实聊天授权动作。

| 布局 | 原版辅助进程结果 |
| --- | --- |
| 完整聊天、侧栏当前项存在 | Observed |
| 仅隐藏侧栏，其他聊天/编辑器/按钮不变 | Blocked，codex-conversation-structure |
| 恢复侧栏 | Observed |
| 增加内置浏览器，侧栏仍在 | 本夹具 Observed；新增 Document 占位节点没有命名 RootWebArea，不能据此声称任意内置浏览器都会失败 |

8 次聚焦断言通过，包含路径分支、上述对照和无点击/前台/鼠标变化检查；不是 8 台设备。故障机两个命名网页根的具体路径由前面的真实只读证据确认，不用夹具的空占位文档冒充同一种 UIA 文档结构。

## 引入时间与漏测原因

Git 中该文档/标题/侧栏三方必须同时存在的判断于提交 `64c746d` 引入，时间为 2026-10-26 14:38:57（UTC+8），当时 VERSION 为 1.1.15 候选，随 1.1.16 正式版发布并沿用到 1.1.22。后来 CDP 绑定复用了原生证明，也继承了此限制。

当时为避免同名聊天或错误页面被点击，采用了依赖完整聊天布局的识别条件。问题在于将侧栏可用性当成唯一聊天身份来源、将整个窗口当成单一文档，覆盖不到正常的紧凑聊天/内置浏览器布局。此前验证主要覆盖完整聊天及自有控件窗口，遗漏本布局，是实现和测试覆盖不足；不是用户误操作，也不是仅凭“新增保护”可以解释过去的正常失败。

## 可执行修复方案

1. 从唯一主聊天编辑器及其原生祖先关系定位所属网页文档，限定在该文档找聊天标题/控件，排除内置网页的登录、密码或富文本输入区。整个窗口不再要求只有一个网页文档。
2. 将主聊天页面、当前对话稳定身份、编辑器及实际动作控件绑定起来，支持侧栏收起或聊天压到侧边的正常布局。对故障机的当前聊天数据标记做只读一致性验证；同名聊天、多个 app 页面及错误页必须仍能区分，不能只凭一个标题接受动作。
3. CDP 与 UIA 的页面识别共用这套作用域证明，避免 CDP 仍先被旧的全窗口/侧栏假设挡住；布局变化后自动重新取得同一聊天绑定。
4. 绑定恢复后继续核对故障机当前版本的控件状态和动作入口，不在第一层错误消失时就宣布整个恢复链路通过。不增加草稿条件，不改变 1.5 秒输入让行，不用旧截图或未知控件填补绑定失败。
5. 日志保留文档候选数、主编辑器所属文档、标题/侧栏/对话身份的具体失败阶段；不记录网页登录值或编辑器文本。核验失败时，界面明确区分旧预览与当前不可用状态。
6. 修复验收覆盖完整/紧凑聊天、内置浏览器展开/收起、多个网页和输入区、隐藏侧栏、多 app 页面和同名聊天；先在实机只读确认正确绑定，再核对暂停/恢复闭环，包含遮挡/最小化，不能让登录页控件成为恢复候选。
